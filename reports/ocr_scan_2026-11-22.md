## P0（blocking，真实缺陷会产出错误结论）

### P0-1 流式模式把跨 parquet 文件的同一 episode 拆成多次独立校验，`results` 被最后一个分片覆盖
- 位置：`pipeline/validator/streaming.py:119-147`（关键 123/140/145）
- `iter_frame_chunks` 按 data/*.parquet 逐文件产出（loader.py:1371-1374），而项目自身承认「同一集的两段可能落在不同 parquet 文件」（policy.py:247-248）。episode 跨文件时 `_validate_non_video` 每次只看到单分片行，`results[ep_index] = res` 让末片结论覆盖前面的：
  1. `res.frame_count` 是末片行数而非全集行数 → 帧数区间判定错位，可能误报 `frame_count_abnormal`（hard-drop，剔除合法 episode）；`meta_index_inconsistent` 同理
  2. 前面分片检出的真实缺陷（首片 NaN、时间戳错乱）被覆盖后静默丢失
  3. `pending_video` 对同一集追加多次 → 视频探针按错误 frame_count 比对，可能误报 `frame_mismatch`，且双份 blank 探针名额
- 内存模式（concat 后 groupby）无此问题；streaming.py docstring 声称「与内存模式的差异只有一处」与此不符
- 复核：已由宿主亲自读码复核属实

## P1（高概率 bug / 资源泄漏 / 竞态）

### P1-1 文件枚举把「下一个文件」查成「当前文件」，编号断档即静默截断
- `pipeline/loader.py:850`（配合 857-863）；`_has_next` 应传 `fi + 1` 而传了 `fi`，`not _has_next(...)` 恒 True → 遇到第一个缺失文件编号就 break，glob 兜底因 found 非空不触发，后续 episode 完全静默不进质检

### P1-2 iter_frame_chunks 整数白名单过滤遇字符串 episode_index 列把所有帧静默丢光
- `pipeline/loader.py:1404-1405`；内存路径已在 1033-1039 修过同类问题（to_numeric 归一），流式路径漏修 → 流式质检 + `--max_episodes` + 字符串 episode_index 列 → 产出 0 episode 空结论且无告警

### P1-3 流式模式下单个损坏 parquet 使整次质检中止，与内存模式「毒数据防冲击」降级设计相悖
- `pipeline/validator/streaming.py:119`（经 loader.py:1399-1400）；内存模式记 corrupted_files 继续（loader.py:1017-1023），流式模式 DatasetFormatError 一路抛穿 → exit 3 无报告。恰是为「10–50GB 脏数据」设计的模式最需要降级

### P1-4 policy 裁剪分支只要求「存在可裁剪的 NaN 项」，混合边界/中段坏帧时把不可裁剪的硬损伤当 repair 保留
- `pipeline/policy.py:157-163`（配合 validator/types.py:82-90）；分支条件不检查每个 nan 项 `trimmable=True`，且先于 hard-drop 执行 → 中段 NaN 帧原样进入清洗产物（训练 loss 直接 NaN）

### P1-5 repair_frame 全部点被过滤时返回 0 点帧，破坏「修复后保持 N 点不变」契约
- `pipeline/pointcloud/cleaner.py:214-215`；policy 坏点比例上限不含 outside_ratio → 整帧越界仍判 repair → bounds 过滤清空后写出空 cell；:139 还会把空帧记为 last_good 污染后续占位

### P1-6 空/解析失败 cell 被 `np.isfinite(pts).all()` 空真判定为「好帧」，污染 hold-last-good 占位
- `pipeline/pointcloud/cleaner.py:150`；应先判 `pts.size` 再更新 last_good

### P1-7 output_plan 中被 _rewrite_frames 跳过的 episode 会让 _rebuild_videos / rewrite_episodes_meta KeyError，整次清洗崩溃
- `pipeline/cleaner/manual.py:712`（crash 点）、`pipeline/cleaner/meta.py:108-109`（必然 crash 点）；split 段声明长度超实际行数（meta 谎报 length 正是要处理的脏场景）或整表读取失败时触发——本可降级为跳过+告警，却变成整次清洗 abort

### P1-8 pointcloud patch-cleaned-dataset 模式用源数据集 meta 覆盖主清洗产物 meta
- `pipeline/pointcloud/cleaner.py:177-178`；`copy_meta(src_root, dst_root)` 把脏源 meta 盖回清洗产物（已删 episode 写回、stats 复旧、计数冲掉），且 decisions 按源 (episode_index, frame_index) 定位而产物已重排 → 改错帧。当前 main.py:489 未触发，但属文档化公开 API 行为

### P1-9 verify 验收脚本：validator 层运行失败时判定被静默跳过，脚本仍以 0 退出（PASS）
- `kaggle_ab/verify_datasets.py:262`（复刻于 `kaggle_ab/verify_v2.py:177`）；`run_validator` 返回 ok=False 时判定循环直接 continue，FAIL 检查不触发 → 与 docstring「任何一层失败都非零退出」矛盾，验收门形同虚设

### P1-10 Dashboard 曲线接口在 action/state 列含 null 单元格时抛 TypeError，该 episode 的 API 请求无响应
- `tools/dashboard_server.py:236`（`to_vectors`）；`map(float, None)` 抛 TypeError，do_GET 只捕 BrokenPipe/ConnectionReset → 浏览器拿到连接中断。Dashboard 的用途恰是浏览带缺陷的原始数据集（analyze_action_distribution.py:64-66 已防同类输入）

### P1-11 benchmark_reader.py 依赖未声明的 psutil，缺失时峰值内存静默报 0 且退出码仍 0
- `tools/benchmark_reader.py:50`（结果构造 133-140）；psutil 不在 requirements.txt / requirements-dev.txt / pyproject.toml → ImportError 线程静默死亡，`peak 0 / delta 0` 照常打印 return 0，基准工具输出伪造读数
