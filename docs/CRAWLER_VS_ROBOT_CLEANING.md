## 0. 怎么用这份文档

两个领域表面完全不搭（网页文本 vs 真机轨迹），但清洗方法论是同一副骨架。本文档先对比差异与同质化（第 1–3 节），再把爬虫领域成熟的两套工程思想移植进来（第 4–5 节），指出本仓库现有的盲区（第 6 节），最后给出落地顺序（第 7–8 节）。

每节末尾有检验题，为自学模式——**参考答案集中在附录**。建议先自己作答再核对。

## 第 1 节 · 世界观差异：淘金 vs 验零件

一句话直觉：

- **爬虫清洗**（C4 / FineWeb / LAION 这类）是**在垃圾山里淘金**：数据没结构、没真值，只能用代理指标把最差的三成扔掉，在 PB 级规模下追求"更多更好的 token"。
- **机器人数据清洗**（LeRobot v3 这类）是**在流水线上验零件**：每个 episode 有严格 schema、有时间轴、有物理约束，坏一件轻则 dataloader 崩、重则策略学坏，追求**逐件判决**。

类比：爬虫清洗像**海关抽检集装箱**——量大，只能抽样，凭经验规则放行；机器人清洗像**工厂出厂检验**——每件产品过检具，不合格就修或报废。洗衣厂（本仓库）开在后者那一侧。

这个差异由三个问题决定，后文所有差异都能追溯到它们：

1. **数据有没有时间轴？**（文本没有，轨迹有）
2. **真值能不能验证？**（文本只能猜，物理可算）
3. **错误是统计成本还是结构成本？**（坏一篇网页无感，坏一条轨迹有毒）

## 第 2 节 · 逐项对照

| 维度 | 爬虫数据集 | 机器人数据集（LeRobot v3） |
|---|---|---|
| 数据形态 | 无结构文本/图文对，没有 schema | 严格 schema：`meta/info.json` + parquet + video + 点云分片 |
| 时间的地位 | **不存在** | **一等公民**：时间戳单调、fps 一致、帧-视频对齐、时长匹配 |
| 校验依据 | 只能上代理指标：语言 ID、困惑度、标点比、重复 n-gram——**无法验证"真"** | 可验证约束：关节限位、速度上限、平滑性、state/action 因果一致——**物理可信度可算** |
| 去重粒度 | 文档/段落级语义近似去重（MinHash/SimHash） | 整条 episode 重复 + 冻结帧（本质是**时间轴上的去重**） |
| 错误成本 | 统计性：一篇坏文淹没在十亿 token 里 | 结构性：一个 shape 错的分片让训练崩，一条错动作轨迹直接教坏策略 |
| 清洗动作 | 几乎只有 filter（留/扔） | filter + **repair**（重采样/重编码/裁剪/修 meta）+ **quarantine**（送复核台） |
| 规模策略 | PB 级，流式 + 抽样质检 | GB–TB 级可全量扫描，但视频解码贵 → 窗口化流式校验（本仓库 `validator/streaming.py`） |
| 判定主观性 | 质量高度主观，依赖模型裁判（GPT-2 困惑度、fastText、LLM judge） | 大多客观可测；但"这条轨迹任务完成得好不好"仍需人/VLM 复核（本仓库 `annotation/` 复核台） |
| 合规关切 | 隐私（PII）、版权、毒性、benchmark 污染 | 物理安全、轨迹合理性、train/val 场景泄漏 |

## 第 3 节 · 同质化：同一副骨架

剥掉表层，两边都是同一个**六段流水线**：

1. **标准化解析**：HTML→正文 ≈ 原始日志→LeRobot schema
2. **廉价启发式先行**：标点比/行重复 ≈ 方差/跳变/冻结帧检测——都是"先跑便宜规则，再上贵模型"
3. **分级判决**：keep / drop / quarantine 的分类账（本仓库 `policy.py` 的分诊台）
4. **去重**：精确 hash → 近似匹配，两阶段完全同构
5. **污染防控**：benchmark 泄漏 ≈ 验证集场景泄漏进训练集
6. **全程审计留痕**：丢什么、为什么丢、可复现

而且思想是**双向搬运**的：

| 从爬虫领域 | 搬到机器人领域 |
|---|---|
| MinHash 分片去重 | 对视频滑窗做哈希，检测重复片段/回环动作 |
| GPT-2 困惑度过滤 | **动作可预测性过滤**：用 action prediction error 当"轨迹困惑度" |
| FineWeb 用种子集训练 fastText 分类器 | 用复核台标注过的 episode 训质量分类器，把人工复核扩成自动预筛 |
| LLM-as-judge 给网页打分 | VLM-as-judge 给轨迹打分 |

反过来也成立：本仓库的"逐件判决 + 修复 + 复核"思想，正是爬虫领域在医疗/法律等**高风险语料**子集上开始采用的做法。

本质原因：两者都是**"为下游训练服务的观测数据质量管理"**，GIGO 原则不分领域。

## 第 4 节 · 移植 I：分级采样质检

爬虫领域有一条铁律：

> **便宜检查做普查（census），昂贵检查做抽样（sampling）**——而且抽的不是"随机"，是"分层 + 边界带"。

机器人数据量虽小，但视频/点云解码同样贵，这条铁律直接适用。

### 4.1 FineWeb/CommonCrawl 做法 → 本仓库映射

| 爬虫领域 | 移植到本仓库 |
|---|---|
| 分层 QC：按域名/语言/快照分层看指标，防"整体均值掩盖局部垃圾" | 按**机器人型号 / 任务 / fps / 时长桶 / 模态组合 / 采集批次 / 操作员**分层看留存率 |
| 边界带复核：专审贴近阈值的样本，信息量最大 | validator 报 **warning（非 error）且贴近阈值**的 episode 优先送 `annotation/` 复核台，而不是随机抽 |
| Golden set 回归：人工种子集防规则改动漂移 | 复核台判过的 episode 固化成 golden set；validator 每次改动后重跑，防"修复引入回归" |
| 留存率监控：某层留存率骤降 = 规则误伤 | 黑屏检测突然刷掉某批次 30% → 先怀疑**采集侧**，反馈采集，而不是改阈值 |
| 冒烟先行：小样本跑通全流程再放量 | 已有 `exports_smoke_fps/`、`exports_smoke_dropreview/`——把它**制度化**为固定冒烟集 |

### 4.2 两个关键原理

**分层必须含过程变量。**很多坏法是过程缺陷而非数据类型缺陷：标定漂移、相机线材接触不良、采集 SDK 某周版本的编码 bug、某个操作员的摇杆死区习惯——分布和"谁、什么时候、用哪套设备"强相关。只按型号/任务分层，坏批次会被摊薄成全局小数点。爬虫按快照/域名分层，道理相同：**缺陷由生产过程产生，所以按过程变量分层**。

**边界带复核的信息量原理。**随机样本大多远离阈值，标注它约等于贡献 0 bit；边界带样本恰好在决策函数翻转处，是**对定标阈值信息量最大的样本**（主动学习里的不确定性采样）。留存率对阈值的敏感度全部集中在边界带——每一条边界样本都在直接告诉你"规则该不该挪"。

**留存率异常的排查顺序**（留存率 98%→60% 这类事件）：变化只可能来自三方——**数据、规则代码、阈值配置**。

1. 输入变了吗？把跌幅按采集批次拆开：集中在某新批次 → 数据问题；摊在老批次 → 不是数据
2. 跑 golden set：同一批评定过的 episode 若突然失败 → 代码变了（本仓库历次修复都可能挪判决，如"视频窗缺失时跳过黑屏检测"）
3. 看指标分布直方图 vs 阈值：阈值动了、代码动了、还是数据动了
4. 三者都排除，才定性为真实数据劣化，反馈采集侧

本质：golden set = 固定的数据参照，版本固定 = 固定的代码参照——**数据管道的回归测试 + 二分定位**。

## 第 5 节 · 移植 II：repair 决策树与审计闭环

### 5.1 判决梯子

repair 不是"修 vs 扔"二选一，是一架梯子：**自动修 → 裁剪 salvage → 报废**。判据只有两条：

- **损坏是局部的还是全局的？**
- **修复动作是否改变了下游语义？**

类比（衔接洗衣厂）：扣子掉了自己缝上（确定性重算，直接洗）、袖子破了改短袖（裁剪保残值）、料子霉了整件扔（报废进隔离区）。`policy.py` 的 `_decide_one` 已经实现了这架梯子的骨架（keep / repair / review / drop）。

### 5.2 决策树

```
损坏?
├─ 结构性（meta缺失/dtype错/index错位）
│   ├─ 能由数据其他部分确定性重算 → 自动修（算 episode 长度、重写 index）
│   └─ 来源冲突 → 升级人工，禁止静默择一
│        （本仓库 fix(loader)"同集多行冲突不再静默去重"正是这条）
├─ 时序性（fps错/漂移/帧-视频错位）
│   ├─ 修正量有界（<1帧） → 重采样自动修
│   └─ 超界 → 裁剪或报废
└─ 内容性（黑屏段/冻结段/动作异常值）
    ├─ 局部 → 在准静止点裁剪；不在静止点 → 拆成两条 episode
    ├─ 全局 → 报废 + 送复核台确认
    └─ 判定不了 → quarantine（永远不自动猜）
```

### 5.3 机器人特有的裁剪约束（爬虫没有的）

文本随便剪，接缝无所谓；**轨迹剪一刀，拼接处速度/加速度会跳变**——dataloader 不报错、schema 全部合法，但策略会学到"瞬移"。所以：

> 裁剪必须落在**准静止点**（机器人复位/静止的时刻）；不在静止点，宁可把前后段拆成两条 episode。

这是"合法但错"的典型盲区（第 6 节展开）。

### 5.4 不可逆性原则

修复分两档：

- **可逆/派生型**（由数据重算而来）：自动执行，随便修
- **有损型**（裁剪、重采样）：必须留痕——修复前后各留指纹（哈希）、原始分片不删、审计日志记 reason code

修复必须**可复现、可撤销、可审计**。

### 5.5 审计日志闭环（"越用越准"）

审计日志不是合规文书，它是**过滤器的训练集**。闭环：

```
validator 判决 → 复核台人工裁决 → 判决回流 → 更新阈值 + golden set → validator
```

三条用法：

1. **按规则统计精度**：规则 X 举报的所有样本里，人确认了多少？精度低的规则放宽阈值；从不触发的规则要警惕（检测器腐烂）
2. **翻案记录是金子**：规则说 drop、人说 keep 的样本 = 最高信息量的边界样本，直接入 golden set，并成为规则的新边案
3. **reason code 必须机器可读**：审计日志写"看起来卡住了"就无法聚合；写成 `FROZEN_FRAME, dur=2.3s` 才能按规则聚合出精度表

这就是 FineWeb 拿人工标注种子集反复调分类器的做法，在管道层面就是**主动学习**。

## 第 6 节 · "合法但错"的盲区

schema 校验检查的是**形式合法**（每列 dtype/shape/范围），抓不住**语义损坏**（帧与帧之间的关系错）。四类典型形态：

| 形态 | 什么会逃过现有校验 | 便宜检测统计量 | 主要误报源 |
|---|---|---|---|
| **拼接跳变** | schema/index/黑屏全绿 | 关节序列二阶差分（速度）p99 超执行器物理限速；拼接点单帧孤立尖峰 | 真实碰撞、抓取接触瞬间 |
| **状态-动作因果断裂** | 各通道独立看都合法 | 滑窗回归增益（a_t → Δs_t）持续≈0；互相关滞后漂移 | 被动拖拽/外力干预段 |
| **时间轴病（漂移型）** | 单帧容差检查通过 | 累计漂移：episode 末帧 vs 首帧的帧-视频偏差；时间戳间隔直方图尾部 | 编码器 B 帧导致的正常抖动 |
| **物理不可达** | 各关节限位单独合法 | FK 残差：FK(q_t) 与记录的末端位姿差；"隔空取物"：夹爪远离但物体点云移动 | 记录位姿的坐标系标定误差 |

**核心思想：用物理冗余互证。**这四类的共同解法是让多通道互相印证——video vs 关节、FK vs 记录位姿、action vs Δstate。爬虫文本没有第二通道，只能上模型裁判；机器人数据天然多通道，这是它"可验证性"优势的兑现处。

**误报处理原则**：这些统计量的误报源（碰撞、接触、外力）恰恰是高价值数据——所以检测结果全部走"边界带 + 复核台"，**不直接 drop**（呼应"轨迹困惑度会误杀恢复行为"）。

本仓库 `validator` 的 `check_action_jump` 已是这类检查的雏形（动作跳变），第 6 节是它的系统化清单。

## 第 7 节 · 落地路线图（本仓库）

**已有盘点**：

- 结构校验：schema / index / loader（含冲突不静默去重）
- 内容检查：点云特护线、黑屏流式检测（`validator/streaming.py`）、`check_action_jump`
- 分诊：`policy.py`（keep / repair / review / drop 四档）
- 人工复核台：`annotation/`
- 冒烟：`exports_smoke_fps/`、`exports_smoke_dropreview/`
- 审查机制：六轮 audit + `docs/REVIEW_FIXLIST.md`

**缺什么、建议顺序**（依赖关系决定顺序，不是重要性）：

| # | 事项 | 依赖 | 成本 |
|---|---|---|---|
| 1 | **审计日志 schema 化**（episode_id, rule, metric_value, threshold, verdict, human_override, reason code） | 无 | 低——一切下游分析的地基 |
| 2 | **分层留存率报表**（批次/操作员/型号/任务/fps 分桶） | 1 | 低——只读 parquet/meta，零解码 |
| 3 | **边界带队列**（warning 且 metric 处于阈值 ±ε 带内 → 自动进复核台队列） | 1, 2 | 中 |
| 4 | **golden set 固化 + 回归跑**（复核台裁决过的 episode 固化，validator 每次改动后重跑） | 1 | 低——直接保护六轮审查的每次修复 |
| 5 | **物理冗余检查**（第 6 节四统计量） | 1 | 高——研究性强，先离线跑不进门禁 |
| 6 | **修复分级实现**（auto / trim / split / quarantine 四档 + 有损修复前后指纹） | 1 | 中——`policy.py` 已有骨架，补"准静止点"约束与指纹 |
| 7 | **闭环周报**（per-rule precision、翻案率、检测器腐烂报警） | 1, 3, 4 | 中 |

**为什么这么排**：1 是数据结构地基；2/3 低成本高确定性；4 立刻保护正在进行的修复工作；5/6/7 依赖 reason code 和复核台的流量，放后。

## 附录 · 检验题全集与参考答案

### 第一轮：领域对比

**Q1 爬虫清洗里几乎不存在 repair，为什么机器人清洗里 repair 是一等公民？**

repair 有两个前提：**知道"正确形态"是什么 + 有冗余可以重建**。LeRobot v3 schema 定义了每列的 dtype/shape/fps，错在哪、该修成什么样是明确的；时间轴提供了重采样、裁剪、重编码这类"用邻帧重建"的冗余；而且一条 episode 是真机采集的昂贵产物，扔掉代价高——所以修有 ROI。网页没有"正确文本"的定义，坏是语义坏不是结构坏，单篇价值趋近零——修没有 ROI。爬虫里仅有的"修"（去 boilerplate、转编码）其实是解析/归一化，不叫 repair。一句话：**repair = 用结构定义目标、用冗余重建信息，机器人数据两样都有，文本两样都没有**。

**Q2 数据集里出现 1000 条完全相同的 episode，两个领域各怎么处理？**

思想同构：先精确 hash 后近似匹配；但**粒度**不同——爬虫在文档/段落级（价值在语义内容），机器人在 episode 级内容签名（action+state 序列哈希）外加帧级（冻结帧就是时间轴上的重复）。更深差异在**根因**：网页重复是媒介常态（一篇文章转载到十个站），去重是日常；机器人数据出现 bit 级重复，几乎必然是采集/导出流水线把同一条写了两次——去重命中从"日常清理"变成**报警器**，该去查是谁写的，而不是默默删掉（呼应 `fix(loader)`"同集多行冲突不再静默去重"）。如果是 1000 条**近似**相同（微小抖动）？爬虫当垃圾去重，机器人当正常演示重复——问题从"去重"变成"分布均衡"，手段是重采样/加权，不是删。**同一输入，两个领域判决可以相反。**

**Q3 设计一个"轨迹困惑度"，它会误杀什么好数据？**

设计：先用便宜统计打底（jerk、动作跳变），再训一个小的 forward-dynamics 模型，用 `a_{t+1} | o_{≤t}, a_{≤t}` 的预测误差按 episode 聚合。必然误杀三类好数据：①**纠正/恢复段**（专家手抖后快速修正，从历史看不可预测，但恰恰是策略最该学的）；②**首次出现的新场景**（高意外 = 高价值多样性）；③**接触密集操作**（碰撞、打滑天然随机，误差高是物理不是噪声）。深层对照：GPT-2 困惑度杀掉诗歌和代码，轨迹困惑度杀掉恢复行为——两者都把"可预测 = 好"编码进过滤器，对长尾天然不公，所以尾巴都要交给人审/VLM（本仓库 `annotation/` 复核台）。

### 第二轮：分级采样质检

**Q1 分层为什么必须含采集批次/操作员？**

因为很多坏法是**过程缺陷**，不是数据类型缺陷：标定漂移、相机线材接触不良、采集 SDK 某周版本的编码 bug、某个操作员的摇杆死区习惯——分布和"谁、什么时候、用哪套设备"强相关，和机器人型号/任务弱相关。只按型号/任务分层，坏批次会被摊薄成全局小数点。爬虫按快照/域名分层，道理相同：**缺陷由生产过程产生，所以按过程变量分层**。

**Q2 边界带复核为什么比随机复核信息量大？**

随机样本大多远离阈值，判决一目了然，标注它约等于贡献 0 bit；边界带样本恰好落在决策函数翻转处，是**对定标阈值信息量最大的样本**（主动学习的不确定性采样）。留存率对阈值的敏感度全部集中在边界带——随机复核对这个导数一无所知，边界复核每一条都在直接告诉你"规则该不该挪"。

**Q3 留存率 98%→60%，排查顺序？**

变化只可能来自三方：**数据、规则代码、阈值配置**。①输入变了吗——把跌幅按采集批次拆开：集中在某新批次 → 数据问题；摊在老批次 → 不是数据。②跑 golden set——同一批评定过的 episode 若突然失败 → 代码变了。③看指标分布直方图 vs 阈值——阈值动了、代码动了、还是数据动了。④三者都排除，才定性为真实数据劣化。本质：golden set = 固定的数据参照，版本固定 = 固定的代码参照——**数据管道的回归测试 + 二分定位**。

### 第三轮：repair 与审计

**Q1 轨迹中间剪一段直接拼接，schema 全绿、dataloader 正常——问题出在哪层？怎么抓？**

问题出在**语义层**：schema 只约束单帧/单列的形态，不约束帧间导数连续性；拼接处的速度/加速度跳变不违反任何列约束。抓法：对关节序列做二阶差分（或速度），拼接点表现为孤立的极端尖峰；更严格的判据是超过执行器物理限速——**物理上不可能 = 必有损坏**。注意误报源是真实碰撞/接触瞬间（高价值数据），所以命中后送边界带复核而非直接 drop。

**Q2 什么样的修复允许不经人审自动执行？**

判据是**可判定性**，不是置信度：修复结果能由数据自身**确定性重算**、重跑结果唯一、不改变语义 → 自动执行（如由 parquet 行数重算 episode 长度、重写 index）。凡"正确值不唯一"（需要插值/猜测）的，都是有损修复 → 走梯子后两档 + 留痕。置信度高只说明"大概率修对"，不说明"修法唯一"——所以不能拿置信度当自动执行的条件。

**Q3 审计日志里哪类记录对调阈值信息量最大？**

**翻案记录**（规则说 drop、人判 keep）。规则正常命中且人确认的样本落在分类器深处，梯度≈0，只巩固现状；翻案样本恰在决策面翻转处，每一条都直接指出"阈值错了、规则错了还是数据错了"，是阈值定标和 golden set 的最高价值来源。
