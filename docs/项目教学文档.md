## 1. 项目定位

### 1.1 一句话

这是一个面向 LeRobot v3 机器人数据集的**数据治理流水线**：把「加载 → 质检 → 分级处置 → 报告 → 清洗 → 可视化」串成一条可复现的链路，不包含任何模型训练代码。

### 1.2 为什么机器人数据需要它

机器人模仿学习对数据质量极其敏感，而最危险的问题往往是**静默的**——训练不会报错，只是学不会：

1. **数值坏死**：一段 112 帧里混着 11 帧 NaN，会让 loss 直接爆掉（这算幸运的）。
2. **结构错位**：视频帧数与 state 行数不一致、mp4 被截断，训练管线会静默地学到错位数据。
3. **统计过期**：`meta/stats.json` 的 mean/std 与真实数据不一致，归一化全错。
4. **采集污染**：遥操作接管导致 action 跳变、空转 episode、重复入库、镜头遮挡黑屏。

LeRobot 官方工具链只有「加载」和「编辑」，没有质检层。这个项目补的就是这一层。

### 1.3 它做什么、不做什么

做：

- 13 条逐 episode 规则代码 + 1 条数据集级规则（`stats_stale`）；报告按 13 类归并展示
- 严重度分级（error/warning/info）与处置动作（keep/repair/review/drop）
- 人工复核回灌（override）、修复留痕、报告可 diff
- 输出一份可直接训练的新数据集（删除 + 修复 + 索引重映射 + 视频重建 + stats 重算）
- 增量模式与流式模式，适配大数据集与机械盘

不做：

- 不训练模型、不做数据增强、不做标注
- 不修改源数据集（严格只读）
- 不保证修复后的视频画质完全无损（libx264 重编码，crf20）
- 单机单进程；更大规模需要按 parquet 文件并行

## 2. 系统全景

### 2.1 六阶段流水线

```
dataset/ ──► loader ──► validator ──► policy ──► reporter ──► cleaner ──► visualizer
               │            │            │           │            │            │
           只读视图      证据+严重度    处置动作     JSON/CSV    新数据集      5 张图
```

- 入口：[main.py](../main.py)，它只负责编排、日志、错误处理和中间结果落盘。
- 每个阶段都把产物写到 `<output_dir>/intermediate/`，**任何一步挂了，前面的产物仍然可用**。
- 清洗失败不会丢弃报告（`main.py` 里 cleaner 的异常只记录，不中断）。

## 3. 架构设计

### 3.1 分层与依赖方向

```
main.py
  ├─ loader（无依赖）
  ├─ validator/streaming → validator/context → rules → probes
  ├─ policy（依赖 validator 的类型 + loader 的视图）
  ├─ reporter（依赖 loader + validator + policy）
  ├─ cleaner（依赖 loader + policy 的处置结果）
  └─ visualizer（只读 loader + validator + 清洗结果）
```

依赖是**单向**的：后一层可以读前一层，前一层不知道后一层存在。这样 `validator` 可以被单测直接调用，不需要构造整个流水线。

### 3.2 五个关键设计决策（重点讲这五个）

#### 决策一：loader 只读，结论全部在 validator

新手常见写法是「读数据时顺手判空、顺手删异常行」。这样做的后果：

- 想换规则就必须改读取逻辑；
- 想复用一个数据集做多种策略对比，做不到；
- 单测必须造真实文件。

本项目让 `LeRobotDatasetView` 只承载数据与元信息，所有判断都在 `validator`，所有修改都在 `cleaner`。

#### 决策二：阈值自适应，而不是拍脑袋写死

不同机器人的关节单位、控制频率、动作幅度完全不同。写死「action 跳变 > 5 就异常」必然误报。

本项目的做法是**从数据集自身分布推导**：

```text
帧数区间（context._resolve_frame_bounds）：
  median = median(counts)
  mad    = median(|counts - median|)
  sigma  = 1.4826 * mad          # 让 MAD 与标准差同量纲
  low    = max(floor,   median - k_low  * sigma)   # k_low 默认 3
  high   = min(ceiling, median + k_high * sigma)   # k_high 默认 8

action 跳变逐维阈值（context._thresholds_from_arrays）：
  thr_d = max(abs_floor, median|Δ_d| + mad_k * 1.4826 * MAD|Δ_d|)
  abs_floor 是安全下限（默认 1.0），mad_k 默认 12
```

配置里的 `floor/ceiling/abs_floor` 只是**安全下限/上限**，不是主判据。换机器人不用改代码，只需要在 `config/default.json` 的 `robots` 里覆盖少量参数。

#### 决策三：严重度 ≠ 处置，能修不删

真实业务里删数据是不可逆的，而且大量异常是可救的：

| 现象 | 新手做法 | 本项目做法 |
|---|---|---|
| 首尾各 3 帧 NaN | 整条删 | 裁掉首尾，保留 episode（repair/trim） |
| 时间戳乱序 | 整条删 | 用 `frame_index/fps` 重建时间轴（repair/timestamps） |
| meta length 漂移 | 整条删 | 按真实行数重建 meta 索引（repair/index） |
| stats.json 过期 | 不管 | 数据集级统计，清洗时重算 stats |
| 中段 NaN / 视频错位 / 空转 | 删 | 删（error/drop） |
| action 跳变 | 删 | 转人工复核（warning/review） |

所以规则只产出**严重度 + 证据**，处置由 policy 层统一决定。

#### 决策四：质检是流程，不是一次性脚本

- **人可以推翻结论**：`review_queue.csv` 填 `reviewer_disposition`，用 `--overrides` 回灌；报告标注「人工覆盖 N 条」。
- **结论可追溯**：报告带数据集指纹、配置快照、自适应阈值推导依据；清洗写 `quality_cleaning_notes.json`。
- **结论可复用**：manifest 记录每个 episode 的签名，数据没变就复用历史结论。
- **源数据零改动**：`cleaner.assert_safe_output` 禁止输出目录等于/位于源数据集内，且有单测。

#### 决策五：规模与 IO 的现实约束

- 视频探针先读容器元数据（`nb_frames`/`duration×fps`），只有必要时才全解码；黑屏检测一次 ffmpeg 调用抽多帧。
- 视频探针有界并发，默认 `probe.max_workers=2`（机械盘友好，SSD 可调高）。
- `--streaming` 按 parquet 文件两遍扫描，内存峰值约等于一个文件，而不是整表。
- `--incremental` 只重检变化的 episode，避免重复视频探针。

### 3.3 核心数据模型

| 结构 | 位置 | 关键字段 | 作用 |
|---|---|---|---|
| `LeRobotDatasetView` | `pipeline/loader.py` | `info/stats/features/tasks/episodes/frames/video_index/data_files` | 只读数据视图 |
| `DatasetContext` | `validator/context.py` | `frame_bounds/action_thresholds/fingerprints/issues/resolved` | 数据集级上下文 |
| `EpisodeResult` | `validator/types.py` | `reasons/details/frame_count` | 单 episode 的结论与证据 |
| `ValidationResult` | `validator/types.py` | `results/resolved_thresholds/dataset_issues/skipped_checks/aggregates` | 质检总结果 |
| `Decision` | `pipeline/policy.py` | `disposition/severity/reasons/repair/trim/source` | 处置动作 |
| `CleaningResult` | `cleaner/types.py` | `removed/repaired/repairs/verification/output_root` | 清洗结果 |
| `QualityManifest` | `pipeline/manifest.py` | 配置摘要 + episode 签名 + 缓存结论 + 清洗结果 | 增量状态 |

一个 `EpisodeResult` 里，`reasons` 是机器可读的规则代码，`details` 是给人看的证据（第几帧、哪个维度、阈值多少）。**报告之所以能被人复核，靠的就是 details。**

### 3.4 两种运行模式

| 模式 | 触发 | 读数据方式 | 阈值来源 | 清洗 |
|---|---|---|---|---|
| 默认全量 | 无参数 | 整表进 pandas | 全量 episode | 支持 |
| 增量 | `--incremental` | 元信息扫描 + 只重检变化 episode | 缓存 + 变化后重算 | 支持，计划不变则复用 |
| 流式 | `--streaming` | 每个 parquet 文件读一次，共两遍 | 采样前 200 个 episode | 自动跳过 |
| 增量 + 流式 | 两者同时 | 分片 + 复用结论 | 采样 + 缓存校验 | 自动跳过 |

增量与流式可以组合，但 `--max_episodes` 与增量互斥（main 会告警并按全量处理）。

## 4. 核心代码逻辑

### 4.1 loader：只读视图

入口：

```python
load_dataset(path, max_episodes=None, *, load_frames=True) -> LeRobotDatasetView
```

它做四件事：

1. **读元信息**：`meta/info.json`、`meta/stats.json`、`meta/tasks.parquet(.jsonl)`、`meta/episodes/**.parquet`。
2. **发现数据文件**：按 `info.json` 的 `data_path` 模板（`data/chunk-{chunk}/file-{file}.parquet`）或 v2.1 的 `episode_XXXXXX.parquet` 布局。
3. **读帧**：`load_frames=True` 时用 pyarrow 读所有 parquet；`max_episodes` 生效时用 `filters=[("episode_index","in",keep)]` 做**下推过滤**，只读需要的行。
4. **建立视频索引**：`videos/<camera>/chunk-xxx/file-xxx.mp4` → `{(chunk,file): path}`，再结合 episodes 元信息里的 `from_timestamp/to_timestamp` 定位每个 episode 的视频片段。

视图提供的关键能力：

| 方法/属性 | 用途 | 流式模式行为 |
|---|---|---|
| `num_episodes` / `episode_indices` | episode 列表 | 读 meta |
| `num_frames` | 总帧数 | 退回 meta `length` 求和 |
| `frames_by_episode()` | episode → 帧数 | 读 meta `length` |
| `frame_count_of(ep)` | 单 episode 帧数 | 读 meta `length` |
| `episode_frame(ep)` | 取整段帧（排序后） | 按 episode 过滤读 parquet |
| `task_of(ep)` | 任务描述 | 优先 episodes meta，其次 frames 的 `task_index` |
| `video_location(cam, ep)` | 视频文件 + 时间窗 | 与内存模式一致 |
| `summary()` | 报告用的概览 | schema/columns 退回 info.json |

`iter_frame_chunks(view, columns=None, episodes=None)` 是流式 API：按 `view.data_files` 顺序，一次产出一个 parquet 的 DataFrame，并按需只读指定列、只取指定 episode。内部字段 `SOURCE_COL` 记录来源文件，供 cleaner 按原文件重写。

> 为什么强调 `max_episodes` 用 pyarrow filter：对 50GB 数据集，先读全表再 pandas 过滤等于把 IO 和内存都浪费一遍。

### 4.2 validator：证据生产

主流程（`validator/__init__.py`）：

```text
build DatasetContext（阈值、指纹、数据集级问题）
for 每个 episode:
    _validate_non_video(...)       # 数值 + 结构 + meta 一致性
    放入 pending_video
_run_video_checks(pending_video)   # ffprobe 帧对齐 + ffmpeg 黑屏抽帧
汇总 ValidationResult
```

关键点：

- **两阶段执行**：非视频规则是纯 CPU，先跑；视频探针是进程等待，放后面用 `ThreadPoolExecutor` 有界并发，默认 2 路。
- **增量复用**：`prior` 保存历史 `EpisodeResult`，`only` 指定本次重检的 episode；复用时**只重算重复项**（`_refresh_duplicate`），因为重复判定依赖全局，其他 episode 增删会影响结果。
- **跳过原因要留痕**：没有 ffmpeg/ffprobe、没有视频特征、没有 action 列时，写入 `skipped_checks`，报告里如实展示，而不是假装检查过。

#### DatasetContext：数据集级判断

`context.py` 负责五件事：

1. **帧数区间**（见 3.2 公式）。
2. **action 逐维阈值**：把每个 episode 的 action 转成矩阵，算相邻帧差的绝对值，跨 episode 堆叠后取 median/MAD。
3. **stats 时效性**：采样前 N 个 episode（默认 200）的 state，算实际均值，与 `stats.json` 的 mean 比较：

   ```text
   deviation_d = |actual_mean_d - recorded_mean_d| / max(|recorded_mean_d|, 1e-6)
   最大偏差 > 0.05 → stats_stale
   ```

   维度不一致直接报 `stats_stale`（这会让归一化全错）。
4. **全局 index 连续性**：`index` 必须铺满 `0..N-1`。内存模式用 `np.unique`；流式模式只累计 `(行数, 去重个数, min, max, NaN 数)`，在「行数等于取值范围」的前提下等价。
5. **重复指纹**：把 action 序列按 `quantize_decimals`（默认 3 位）量化后做 SHA1，`fp -> 首次出现的 episode`。指纹覆盖**全部** episode，所以增量模式仍能发现「新增 episode 与历史 episode 重复」。

#### 规则逐条要点（`rules.py`；`stats_stale` 在 `context.py`）

下表把 `nan_state` / `nan_action` 合并成一行展示；两者在代码里是两个独立规则代码。最后一行是数据集级规则，不参与单 episode 处置。

| 规则 | 实现要点 | 默认严重度 | 默认处置 |
|---|---|---|---|
| `nan_state` / `nan_action` | 统计 NaN/Inf；若坏帧只在首尾且占比 ≤ 25%，标记 `trimmable` | error | 可裁则 repair/trim，否则 drop |
| `action_jump` | 逐维阈值比较相邻帧差；记录最差帧/维度/前 5 个例子 | warning | review |
| `frame_count_abnormal` | 与自适应区间比较，区分 `too_few/too_many` | error | drop |
| `timestamp_not_monotonic` | 缺列/NaN/非严格递增；给出重建提示 | warning | repair/timestamps |
| `timestamp_step_deviation` | 相邻时间差偏离 `1/fps` 超过 25%，仅记录 | info | keep |
| `frame_mismatch` | 用 from/to 时间窗换算视频帧数，允许 ±1 帧；处理 mp4 缺失/截断/无法探测 | error | drop |
| `meta_index_inconsistent` | episodes meta 的 `length` 与 parquet 实际行数不一致 | warning | repair/index |
| `missing_task` | 任务描述为空或 `task_index` 无法解析 | warning | review |
| `static_episode` | state（或 action）整段标准差低于阈值 → 空转 | error | drop |
| `blank_video` | 一次 ffmpeg 调用按 2fps 抽 64×48 灰度帧，亮度标准差 < 4 的占比 ≥ 60%（默认只查第一个相机） | error | drop |
| `duplicate_episode` | action 指纹命中更早 episode | error | drop |
| `joint_limit_violation` | 超出配置的 lower/upper（默认关闭） | error | drop |
| `stats_stale`（数据集级） | 见上，不挂在单个 episode 上 | warning | 不进 episode 处置；清洗时重算 stats |

**证据结构**（`EpisodeResult.add`）是这套系统的核心资产：

```json
{
  "action_jump": {
    "jump_count": 3,
    "max_delta": 7.82,
    "worst_frame": 41,
    "worst_dim": 2,
    "thresholds_used": [1.0, 1.2, 1.5],
    "examples": [{"frame": 41, "dim": 2, "delta": 7.82, "threshold": 1.5}]
  }
}
```

有了这些，复核的同学不需要重新跑数据，就能判断「这是真实动作突变还是标注错误」。

### 4.3 streaming：为什么是两遍扫描

流式模式（`validator/streaming.py`）不是「一边读一边判」就够，因为**有些判断依赖全局信息**：

- action 阈值需要跨 episode 的分布；
- 重复指纹需要知道「谁是第一次出现」；
- 帧数区间需要所有 episode 的帧数；
- index 连续性需要全表统计。

所以拆成两遍：

| 阶段 | 读哪些列 | 产出 | 内存 |
|---|---|---|---|
| Pass 1 | `episode_index/frame_index/index/action`（有 stats 时加 `state`） | 帧数区间、action 阈值（采样）、stats 时效均值（采样）、index 统计、指纹表 | 只保留采样 episode 的数组 + 小字典 |
| Pass 2 | `episode_index/frame_index/timestamp/state/action/task_index` | 逐 episode 规则结论、`frames_by_episode`、字段 min/max/mean/NaN/Inf | 一个 parquet 文件 |

最后统一跑视频探针。`ValidationResult.aggregates` 把 Pass 2 的聚合结果交给 reporter，因为此时 `dataset.frames` 是空的。

与内存模式的**唯一实质差异**：action 阈值与 stats 均值来自采样（`streaming.action_sample_episodes`，默认 200），而不是全量。其余规则、严重度、证据完全复用同一个 `_validate_non_video`，因此不会出现「两套规则慢慢跑偏」的问题。

其他细节：

- `--max_episodes` 生效时，两遍扫描都只读保留的 episode（pyarrow filter）。
- 无 `stats.json` 时 Pass 1 不读 state 列，少读一半列宽。
- 清洗需要整表重写，流式模式暂不支持，main 自动跳过并告警。

### 4.4 policy：处置决策顺序

`policy.decide` 对每个 episode 按**固定优先级**判断：

```text
1) 无 reasons                       → keep
2) 只有 nan 且可裁剪                → repair(trim)
3) 所有 reasons 都是可修项          → repair(timestamps/index)
4) severity == error                → drop
5) severity == info                 → keep（仅记录）
6) 其余 warning                     → review（--on-review drop 时改 drop）
```

固定的顺序很重要：它保证「同一种问题在任何数据集上得到同一种处置」，不会因为规则新增而悄悄改变历史行为。

`overrides` 在自动决策之后覆盖，并记录 `source="override"`；`repair` 被覆盖时清空 trim 参数，避免「人工要求保留但还按旧裁剪方案执行」的歧义。

复核队列只导出 `disposition != keep` 的行，包含视频路径、时间窗、证据摘要，数据同学填完 `reviewer_disposition` 就能回灌。

### 4.5 reporter：把结论讲清楚

`build_report(dataset, validation, decisions, dataset_path=...)` 的输出大致包含：

| 区块 | 内容 | 为什么需要 |
|---|---|---|
| `dataset` | 路径、episode/帧数、机器人类型、schema、相机 | 报告的自描述 |
| `summary` | 有效/异常、处置计数、预计丢弃帧、剩余帧 | 一屏看懂结论 |
| `resolved_thresholds` | 帧数区间、逐维 action 阈值、推导依据（median/MAD） | 解释「为什么这么判」，支持换机器人对比 |
| `reason_frequency` | 每条规则命中多少 episode | 定位系统性问题 |
| `invalid_episode_details` | 每个异常 episode 的 reasons + details | 逐条复核 |
| `dataset_issues` | `stats_stale`、`meta_index_inconsistent` 等数据集级问题 | 单 episode 规则看不到的问题 |
| `field_issue_stats` | state/action 的 min/max/mean/NaN/Inf/跳变 episode 数 | 快速判断分布是否异常 |
| `attribution` | 按 episodes 元数据（采集员/日期/批次）聚合异常率 | 定位「哪批采集有问题」 |
| `checks` / `skipped_checks` | 每条规则影响多少 episode、哪些没跑及原因 | 报告可信度 |
| `artifacts` | 图表、复核队列、清洗产物的路径 | 一处跳转 |
| `dataset.fingerprint` | info 字节 + episode/帧数 + 前 20 个数据文件大小 | 判断两份报告是否同一批数据 |

流式模式下 `dataset.frames` 为空，reporter 自动改用 `validation.aggregates` 里的 `frames_by_episode`、`total_frames`、`field_stats`，其他逻辑不变。

### 4.6 cleaner：删除 + 修复

入口：`clean_dataset(dataset, decisions, output_dir, prefer_cli=True)`。

执行顺序：

1. **安全校验**：`assert_safe_output(dataset.root, output_dir/cleaned_dataset)`，输出不能等于或位于源数据集内。
2. **归一化处置**：`drop → 删除`，`repair/trim → 裁剪方案`，`repair/timestamps → 重建时间轴`，`repair/index → 默认索引重建`，其余保留。
3. **选择实现**：
   - 只有删除且 `lerobot-edit-dataset` 可用 → 走官方 CLI；
   - 存在修复项，或 CLI 不可用/失败 → 走内置实现，并记录原因（不静默降级）。
4. **内置实现**（`cleaner/manual.py`）：
   - 用 pyarrow 的 `table.take` / `set_column` 直接操作 Arrow 表，**不做 pandas 往返**，避免 `fixed_size_list` 的 state/action schema 被破坏；
   - 删除 episode、裁剪首尾帧、按 `frame_index/fps` 重写 timestamp；
   - 重算 episode 索引并做 `episode_index_map`（旧 → 新）；
   - 重建 `meta/episodes`、`meta/tasks`、`meta/stats`、全局 `index`；
   - 视频按原时间窗截取并重编码（libx264, crf20）。
5. **产出校验**（`cleaner/util.verify`）：episode 数、帧数、`length == rows`、视频窗口与行数对齐、index 连续、stats 可解析；不通过写入 `warnings`，报告里可见。
6. **留痕**（`cleaner/meta.write_notes`）：`meta/quality_cleaning_notes.json` 记录每个 episode 删了什么、修了什么、重映射到哪。

> 为什么修复优先：删数据不可逆，而边界坏帧、时间轴、meta、stats 都是可计算的。demo 里另有 2 个 episode 被判为 `repair`（裁首尾坏帧、重建时间轴），因此没有进入 8 个 `drop`。

### 4.7 manifest：增量模式的正确性

`pipeline/manifest.py` 记录：

- **配置摘要** `config_digest`：配置变了就不复用；
- **每个 episode 的签名**：基于文件路径、大小、更新时间等 stat 信息；
- **缓存的质检结论**：`prior`；
- **清洗结果与签名**：清洗计划不变时复用产出。

两条路径：

1. **快路径**：数据和配置都没变、报告存在、清洗产物存在且校验通过 → 直接返回，不重跑。
2. **部分重检**：找出变化的 episode，`prior` 传历史结论、`only` 传变化集合；其余复用。
3. **阈值失效**：重检后如果 `resolved_thresholds` 与上次不同（例如新增数据改变了 median/MAD），自动回退全量重检。这一步保证增量不会因为全局分布变化而沿用错误阈值。

`--force` 跳过所有缓存。

### 4.8 visualizer：5 张图

| 图 | 回答的问题 |
|---|---|
| 帧数分布 | 帧数区间是否合理，异常 episode 是否集中在尾部 |
| 有效/异常占比 | 整体健康度 |
| 关节曲线（正常 vs 异常） | 异常轨迹长什么样 |
| action 散点 | 跳变点在分布中的位置 |
| 清洗前后对比 | 删了多少、修了多少、剩多少 |

流式模式下，分布图用 `frames_by_episode()`，散点/曲线按采样 episode 调用 `episode_frame(ep)` 逐段读，不会为了画图把整表载入。

### 5.5 输出怎么读

**`quality_report.json`（先看这 4 处）**

1. `summary`：整体结论、预计丢弃帧。
2. `reason_frequency`：哪类问题最多 → 判断是采集流程问题还是个别脏数据。
3. `invalid_episode_details`：逐条证据，重点是 `action_jump.examples`、`nan_state.first_bad_frames`。
4. `dataset_issues`：`stats_stale` 出现说明归一化统计过期，必须修复；`meta_index_inconsistent` 说明 meta 与真实行数漂移。

**`review_queue.csv`**

只列需要人看的行，包含视频绝对路径和时间窗。填写规则：

- `reviewer_disposition`：`keep` / `drop` / `repair`
- `reviewer_note`：写理由，会进入报告留痕

**`cleaned_dataset/`**

- `meta/quality_cleaning_notes.json`：删/修/重映射的完整记录
- `meta/stats.json`：已按清洗后数据重算
- `meta/episodes/**.parquet`：`length` 已与真实行数一致，`episode_index` 已归零重排

**`plots/`**

先看帧数分布和清洗前后对比：如果大量正常 episode 贴着阈值边界，说明 `mad_k` 或 `abs_floor` 需要调整。

### 5.7 常见问题与排错

| 现象 | 原因 | 处理 |
|---|---|---|
| 报告里 `skipped_checks` 有 `blank_video` | 没装 ffmpeg | 安装 ffmpeg 后重跑 |
| `frame_mismatch` 被跳过 | 没装 ffprobe 或数据集无视频 | 正常；报告已标注 |
| `--incremental` 看起来没生效 | 配置/数据签名变了，或阈值变化触发全量 | 看日志中的「回退全量重检」；必要时 `--force` |
| `--streaming` 没清洗 | 设计如此（整表重写不支持分片） | 去掉 `--streaming` 单独跑清洗 |
| action 跳变误报多 | 机器人动作幅度大或单位特殊 | 提高 `action_jump.abs_floor`，或按 `robot_type` 覆盖 |
| 帧数异常误报 | 数据里本来就有长短不一的合法片段 | 调 `frame_count.mad_k_high`，或改 `mode=fixed` |
| `stats_stale` 一直报 | 采集后 stats 未重算 | 用清洗产物（会重算 stats），或在上游重算 |
| 清洗失败 | 磁盘空间/权限/ffmpeg | 报告仍保留；看 `intermediate/failure_cleaner.json` |
| 中文在 Windows 控制台乱码 | cp936 | 代码已 `reconfigure(utf-8)`；仍有问题可用 `chcp 65001` |

## 6. 测试与质量保障

当前 35 项单测，由测试夹具和四个测试文件组成：

| 文件 | 保障什么 |
|---|---|
| `tests/conftest.py` | 构造最小 LeRobot 数据集、正常/异常 episode 生成器 |
| `tests/test_validator.py` | 14 项规则正反例：可裁/不可裁 NaN、自适应 action 阈值、帧数区间、时间戳、任务缺失、空转、重复、stats 时效、固定阈值覆盖、报告契约字段、跳过原因留痕 |
| `tests/test_policy_cleaner.py` | 处置优先级、裁剪/时间轴/索引修复、源数据零改动、清洗不变量 |
| `tests/test_incremental.py` | manifest 快路径、部分重检、阈值变化回退、`--force` |
| `tests/test_streaming.py` | 流式与内存模式的阈值、reason 集合、聚合帧数一致；脏 episode 可检出 |

核心不变量（面试可以重点讲）：

1. **源数据零改动**：清洗前后对源目录做哈希/文件列表比对。
2. **index 连续**：清洗后全局 `index` 铺满 `0..N-1` 无重复。

4. **视频对齐**：每个 episode 的视频时间窗帧数与 state 行数一致（±容差）。
5. **stats 对齐**：清洗后 `stats.json` 与实测数据偏差在容差内。
6. **流式等价**：同一数据集，流式与内存模式产出的阈值、reason、总帧数一致（采样范围内）。

运行：

```bash
python -m pytest -q
```

## 7. 面试讲解话术

### 7.1 30 秒电梯版（给非技术同事）

> 机器人数据里有很多错误不会报错，只会让模型学不会。我做了个体检工具：自动找出 13 类问题，按「保留 / 修复 / 复核 / 剔除」分诊，能修的不删，最后产出报告和一份修好的数据集，还支持人工推翻结论。

### 7.2 3 分钟技术版（STAR）

**Situation（背景）**
具身数据的脏是静默的：NaN 让 loss 爆掉还算幸运；视频与 state 错位、`stats.json` 过期、重复入库，训练不会报错，只会学不会。LeRobot 官方只有加载和编辑，没有质检层。

**Task（目标）**
做一条可复现的数据治理流水线：既能自动发现问题，又能解释证据、支持人工复核、最终产出可训练的数据集。

**Action（三个关键决策）**

1. **阈值自适应**：帧数区间用 `median ± k·MAD`，action 跳变逐维用 `median|Δ| + k·1.4826·MAD|Δ|`。不同机器人单位不同，写死阈值必然误报；配置里的 floor 只是安全下限。
2. **分级处置，能修不删**：边界坏帧裁剪、时间轴重建、meta 索引重建、stats 重算；只有中段 NaN、视频错位、空转这类不可修的才删。人工可以 override，覆盖记录在案。
3. **工程可落地**：视频探针先读容器元数据、并发默认 2 路；`--incremental` 用 manifest 只重检变化；`--streaming` 按 parquet 分片两遍扫描，内存峰值约等于一个文件。

**Result（结果）**
demo 36 个 episode 注入 13 处异常，13 个异常 episode 全部命中且没有误报；处置 24 保留 / 2 修复（裁首尾 + 重建时间轴）/ 2 复核 / 8 剔除；清洗后 28 个 episode、2388 帧，校验 `ok`；35 项单测保障「源数据零改动」等不变量。

**定位**：数据治理工程，不是训练。让进训练的每条数据可信任、可回溯、可复现。

### 7.3 10 分钟现场演示脚本

```bash
# 1. 造数据（30 秒）

# 2. 全量跑（1 分钟）
python main.py --dataset_path demo_dataset --output_dir outputs

# 3. 看报告结论
python -c "import json;r=json.load(open('outputs/quality_report.json'));print(r['summary']);print(r['reason_frequency'])"

# 4. 展示逐条证据
python -c "import json;r=json.load(open('outputs/quality_report.json'));print(r['invalid_episode_details'][:2])"
```

### 7.4 高频追问 Q&A

**Q1：为什么不用大模型/异常检测算法自动判断？**
质检要可复现、可解释、可审计。规则 + 统计量能给出「第 41 帧第 2 维 delta=7.82，阈值 1.5」这种证据；模型给不出，而且阈值会漂移。这里的目标是工程可信，不是刷指标。

**Q2：自适应阈值为什么用 median + MAD，不用均值 + 标准差？**
数据里本来就有异常值，均值和标准差会被异常值拉偏；median/MAD 是稳健统计量，少量脏数据不会改变阈值。`1.4826` 是让 MAD 与正态分布标准差同量纲的系数。

**Q3：阈值会不会误报/漏报？**
会。所以 action 跳变只给 warning 转人工，不直接删；帧数区间留了 `floor/ceiling` 安全边界；报告把推导依据（median/MAD/逐维阈值）全部写出来，误报可以定位并调整。漏报靠规则覆盖和后续复检补。

**Q4：为什么统计视频帧数不直接全解码？**
几十 GB 数据集全解码不可行。优先读 mp4 容器元数据（`nb_frames` 或 `duration × fps`），只有元数据不可信（小文件/缺 nb_frames）时才精确解码。黑屏检测用一次 ffmpeg 调用按 2fps 抽 64×48 灰度帧算亮度标准差，避免逐帧 subprocess。

**Q5：并发为什么默认只有 2？**
探针是进程等待型任务，瓶颈在磁盘。机械盘上并发高会互相拖慢；默认 2 是保守值，SSD 可在配置里调高到 4–8。

**Q6：增量模式怎么保证结果的正确性？**
三层：episode 文件签名（路径/大小/更新时间）判断变化；配置摘要判断策略是否变；重检后比较 `resolved_thresholds`，全局阈值变了就回退全量。清洗复用还要求上次产出通过校验。

**Q7：流式模式为什么要读两遍？一遍不行吗？**
阈值、重复指纹、帧数区间、index 连续性都依赖全局信息，必须第一遍收集统计量；逐 episode 规则和字段统计在第二遍执行。两遍都只驻留一个 parquet 文件，换来内存可控。

**Q8：流式和全量结果能保证一致吗？**
除 action 阈值与 stats 均值来自采样（默认 200 个 episode）外，规则实现完全复用；单测在构造数据集上比对阈值、reason 集合、总帧数与逐 episode 帧数完全一致，36 episode 的 demo 实跑时 `resolved_thresholds`、`reason_frequency`、`field_issue_stats`、`dataset_issues` 也逐字段相同（仅清洗相关字段因流式跳过清洗而不同）。采样足够大时 median/MAD 已稳定；报告会记录实际采样结果。

**Q9：怎么保证不破坏源数据？**
cleaner 入口断言输出目录不等于、也不位于源数据集内；所有写入只发生在 `output_dir/cleaned_dataset`；单测对源目录做前后比对。清洗失败也不会回写源数据。

**Q10：为什么用 pyarrow 而不是 pandas 做清洗？**
LeRobot 的 state/action 是 `fixed_size_list`，pandas 往返容易把定长向量列变成 object，schema 就坏了。`table.take` / `set_column` 能保住 Arrow schema，也避免大表复制。

**Q11：和 LeRobot 官方工具是什么关系？**
互补。官方只有加载和编辑；纯删除场景本项目优先调用 `lerobot-edit-dataset`，存在修复项时强制走内置实现（官方 CLI 只能删不能修），并记录方法，不静默降级。

**Q12：规模上限在哪？下一步怎么扩？**
单机单进程适配数十 GB / 数千 episode。再大需要按 parquet 文件并行：`DatasetContext` 和规则函数都是无状态的，扩展点在 main 的批处理循环，把文件分片到多进程，最后合并 `frames_by_episode` 与阈值统计。

### 9.2 术语表

| 术语 | 含义 |
|---|---|
| episode | 一次完整采集片段，含若干帧 |
| chunk / file | LeRobot v3 的存储分片：多个 episode 合并进一个 parquet/mp4 |
| fixed_size_list | Arrow 的定长向量类型，LeRobot 用它存 state/action |
| MAD | 中位数绝对偏差，稳健的离散度度量 |
| trim | 裁掉 episode 首尾的坏帧 |
| override | 人工复核结果覆盖自动处置 |
| manifest | 增量状态文件，记录签名、缓存结论、清洗结果 |
| streaming | 按 parquet 文件分片两遍扫描，不整表载入 |
| aggregates | 流式模式下 reporter 使用的聚合统计（帧数/字段分布） |

## 10. 一页总结

1. **它是什么**：LeRobot v3 数据体检 + 分诊 + 治疗 + 病历的工具，不训练模型。
2. **它怎么跑**：loader → validator → policy → reporter → cleaner → visualizer，六阶段独立、中间结果可复用。
3. **为什么这么写**：职责分离、阈值自适应、能修不删、人工可推翻、结论可追溯、规模可控。
4. **怎么用**：`pip install` → 造 demo → `python main.py --dataset_path ... --output_dir ...`；大数据集加 `--streaming`，日常增量加 `--incremental`，人工复核用 `--overrides`。
5. **怎么讲**：先讲静默故障，再讲三个业务决策（自适应阈值、分级处置、人工回路），最后讲证据、边界和定位。不要从技术栈讲起。
