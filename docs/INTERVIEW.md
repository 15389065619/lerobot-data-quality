# 面试/技术交流话术

> 这一段是给"讲项目"用的，不是 README 的核心介绍。核心介绍见 [README](../README.md)，设计权衡见 [ARCHITECTURE](../ARCHITECTURE.md)。

## 30 秒版本

我做了一条 LeRobot v3 数据质检清洗流水线：逐 episode 17 条数值/文件规则 + 8 条点云规则（`config/default.yaml` 的 severity 段可直接数：19 条，另两条是数据集级 `stats_stale` 与 IO 级 `episode_read_error`），输出 Keep / Repair / Review / Drop 四档处置，并保证清洗后训练张量形状不变。核心是三件事——阈值从数据集自身分布推导（median+MAD，换机器人不改代码）、能修不删（13 处注入一刀切要删 12 处，实际只删 7 处）、质检结论可被人工推翻且留痕。此外还有在线 Dashboard、训练前预检、类 DVC 版本回滚、人审驱动的阈值建议。

## 3 分钟版本

> **背景**：我从爬虫/自动化数据流程转入机器人数据工程。第一个感受是：具身数据的脏不会在训练时报错给你看——NaN 让 loss 爆掉还算幸运，视频和 state 错位、stats.json 过期这类问题是**静默的**，策略学不动你都不知道为什么。
>
> **我做了什么**：搭了一条 LeRobot v3 质检清洗 Pipeline，核心是三个业务决策：
>
> ① **阈值自适应**——帧数区间和动作跳变阈值都从数据集自身分布（median+MAD）推导，换机器人不用改代码；
>
> ② **分级处置**——能修不删：边界坏帧裁掉、时间轴重建、meta 索引和 stats 重算，只有中段 NaN、视频错位这类不可修的才丢——13 处注入一刀切要删 12 处，实际只删 7 处；
>
> ③ **人工回路**——质检给出建议，人可以 override，覆盖记录在案，质检因此是流程而不是一次性脚本。
>
> **点云扩展**：在真实 LeRobot 点云数据集上补了 8 条规则（NaN/稀疏/退化/重复/离群/越界/颜色/时序跳变）。关键不是规则本身，而是三个契约：
>
> ① 离群半径按「每帧 1-NN 距离中位数 × k」自适应，固定比例在稀疏点云上会全帧误报；
>
> ② 修复后必须还是 N 点，所以用「过滤 → 去重 → 抖动重采样补点」；
>
> ③ 不可修复帧用 hold-last-good 占位，保住 parquet 行数与视频/state 对齐。真实数据故障注入 8 类全命中，修复后行数、点数、schema 元数据全部不变。
>
> **结果**：demo 注入的 13 处异常全部命中（覆盖 12 类规则、0 误报），点云 8 类注入全命中；清洗后复检 0 error，视频帧数与 state 行数逐 episode 对齐；300 个单测保证「源数据零改动」「index 连续」「stats 对齐」「点云定长契约」这些不变量。顺带修掉一个真实误报：夹爪 {-1,+1} 二值维的开合被当成 action 跳变，导致 50/50 episode 全报警——离散维不应参与连续跳变判定。
>
> **定位**：数据治理工程，不是训练。我关心的是让进训练的每条数据可信任、可回溯、可复现——这也是从爬虫清洗迁移过来的核心能力：规则化、可回滚、可验证。

## 可能被追问的点

**Q：为什么不用 ML 做质检？**
A：三个原因。一是**确定性**——训练数据的判定必须可审计，同一个数据集今天判 keep、明天判 drop 是不可接受的；二是**算力**——质检要在采集现场或 CI 里频繁跑，纯 CPU 分钟级比挂 GPU 推理现实得多；三是**冷启动**——自适应阈值从数据自身分布推导，不需要标注样本训练。语义级判断（物体缺失、遮挡、标注错误）明确留给 ML，通过 `review_queue.csv` 契约接入，不需要改架构。

**Q：多进程并发写盘冲突怎么解决？**
A：让冲突在设计上不存在——计算与落盘分离。worker 是纯函数，只读输入、返回可 pickle 的结果，**从不写盘**；结果经 Future 回传，主进程是唯一写者。并发期不落盘、落盘期不并发。另外 Future 完成顺序随机，所以归并后按 `(episode, frame)` 排序重建 dict，保证与串行逐位一致，有测试钉死。

**Q：修复后怎么保证训练侧不受影响？**
A：契约思维。点云修复后必须仍是 `N 点 × D 维` 且保留 `ARROW:extension:name`；parquet 行数、state/action 维度、视频时间窗三者始终对齐；meta 索引重映射归零、stats 重算。训练层不需要为清洗过的数据写任何特殊逻辑。

**Q：和 LeRobot 官方工具什么关系？**
A：是上下游。官方 `lerobot-edit-dataset` 解决"编辑/删除"，本项目解决"诊断/修复/审计"。纯删除场景我直接委托官方 CLI，一旦有修复项才走内置实现。详见 [COMPARISON](COMPARISON.md)。

**Q：为什么不直接用 lerobot-doctor / DataDoctor？**
A：先给结论——**如果只需要一次体检报告，我会直接用它**。它 12 类 check、免装 `lerobot` 包、`--max-episodes` 处理超大集，URDF 物理限位和全帧视频解码审计我根本没有。我做自研只有三条理由，按重要性排：

1. **我要的是处置，不是结论。** 它的输出是 PASS / WARN / FAIL，我的输出是四档处置 + `review_queue.csv` + `--overrides` 回灌；第二次运行必须能复现第一次的结论，所以我得持久化 `severity_overrides`，还不能让 `from_dict` 把它丢掉。
2. **源数据不能被改。** 它的 `fix` / `trim` 是原地改写，而且我读过源码——`backup` 只 `copytree` 了 `meta/`，被重写的 `data/*.parquet` 不在备份里（`fix.py:46-49`）。也就是说改坏数值回不去。这是它的取舍（有 `--dry-run`），但我的场景是「数据是别人给的」，所以源只读、清洗产物独立落盘，事后能回答「原始长什么样」。
3. **子集模式要诚实。** 它 `--max-episodes` 会跳过依赖全量的检查——这是合理设计；我的选择是覆盖不足时**拒绝导出**，因为我要拿报告当结论用，不愿把部分结论当全量结论。

差异在目标，不在优劣。[COMPARISON](COMPARISON.md) 里有一张六条待核实表，凡我不确定的都标了核实方法——**这张表能被推翻，才说明它不是自说自话**。

**Q：规则和开源实现重合，这个项目凭什么叫项目？**
A：规则本来就不该是我的卖点。NaN 检测、时间戳单调性、视频帧数与行数对账，这些是领域常识，谁写都差不多。我把项目价值分三层看：检查规则**可复制**，价值最低；处置流程（复核队列 → 裁决回灌 → 导出护栏）**半可复制**，居中；判断证据**不可复制**——19 个数据集的缺陷处置、4 次系统判错后被证据推翻的过程、一次口径不对导致 300 倍差异的误判。前两层能抄，第三层是有人真的为结论负过责。这轮我又拿两份从没碰过的 Hugging Face 公开集做交叉验证，另外推翻了自己 4 条结论（`docs/EVAL.md` §2.5），其中一条是把没跑过的检查报成「跑过且通过」。

**Q：这个项目最大的不足是什么？**
A：三条，按严重程度排：

1. **检查项覆盖不如社区实现。** 我没有 URDF 物理限位校验——那需要外部真值，我手里 19 个数据集大部分拿不到；也没有全帧解码审计，只做采样探针。这两块 DataDoctor 比我深。
2. **只有代理指标，没有训练闭环。** 清洗是否有效，最终要靠 loss 和成功率验证；我只能测动作分布和跳变指标，所以 §11 里我明确写了"方差在真实规模上不敏感，能稳定观测的是跳变指标"，而不是硬说清洗让数据变好了。
3. **语义层没碰。** 物体缺失、遮挡、标注错误都不在能力范围内；时序规则只看质心平移，纯旋转检测不出来。

## 现场三件套（提前 10 分钟准备好）

1. `python tools/demo.py --force` — 约 14 s，出报告 + 复核队列 + 图 + 数据卡片 + 版本快照，终端里就能指着「保留 24 / 修复 2 / 复核 3 / 剔除 7」讲。

3. 一份 14 GB 真实数据集的 `docs/EVAL.md §2.2`，用来回答「你处理过真数据吗，多大规模」。
4. `docs/EVAL.md §2.5` 加 `python tools/dataset_inventory.py`，用来回答「你只在自攒数据上测过吧」——libero 1693 集在本地，能当场复算 19 个数据集 / 5855 episode，也能当场演示同一份数据在全量和 `--streaming` 下给出不同结论（M1）；libero 已在本机跑过完整轮，端到端 1617 s（1693 ep / 1.94 GB），产物在 `outputs_libero/`，`cleaning.verification` 里结构层 `ok=true`、规则层 `review 1692` 并存——这一屏就是 M1 最好的说明。

## 我不会说的话

- 不说「清洗让模型指标提升了 X%」——我只测了动作分布和跳变指标，§11 已写明方差在真实规模上不敏感，这条只能当代理指标。
- 不说「生产可用/团队在用」——19 个数据集全是我单方面跑的，没有第二个人用过；里面不少数据本来就是公开集，但「用的人只有我」这一条改不了。
- 不说「语义层问题也能做，只是没时间」——物体缺失、遮挡我确实没有能力检测，说出口会被一句「怎么评估」问穿。

### 0. 开场

**★Q0.1 一分钟讲讲这个项目。**
答：一条 LeRobot 数据集的质检与清洗流水线。加载器认 v2.1/v3.0 布局，规则引擎跑 17 条逐 episode 的数值/文件规则加 8 条点云规则，输出 keep / repair / review / drop 四档；能修的不删，删之前先落一份可复核的 CSV，人可以推翻我的判定并留痕，最后产出一个能直接喂训练的干净数据集和一份可 diff 的报告。
数：demo 36 ep / 3008 帧；19 个数据集 / 5855 episode（含 2 份外部公开集）；真实最大 14 GB / 200 ep / 128 万帧；300 个测试，分支覆盖率 73.73%——这条不用信我，Actions 最新一次 CI 的日志里写着 `Total coverage: 73.73%`，公开可读。
追：最难的部分是什么？→ 不是「检测」，是「让结论可复现、可追溯」。

**Q0.2 为什么做这个？**
答：我从爬虫数据流程过来，第一个感受是机器人数据的脏是静默的——NaN 让 loss 爆掉还算幸运，stats.json 过期、视频和 state 错位这类问题不报错，只让策略学不动，而你不知道为什么。

### A. 规则与阈值

**★A1 为什么不用固定阈值？**
答：不同机器人关节单位不一样，同样 0.5 的跳变在机械臂上是故障、在夹爪上是正常开合。所以帧数区间用 median ± k·MAD，action 跳变逐维用 median|Δ| + k·1.4826·MAD|Δ|——换机器人不改代码，只换数据集。
数：`pipeline/validator/context.py:277`。
追：1.4826 哪来的？→ MAD 到 σ 的一致性系数，正态假设下 σ=1.4826·MAD；用 MAD 不用 std，因为脏数据本身会把 std 抬高，等于让脏数据自己给自己放宽标准。

**★A2 那配置里的 floor 是干嘛的？**
答：防整批数据高度一致时阈值塌到 0——MAD≈0 时任何抖动都超阈。floor 是安全下限，而且报告会写 `abs_floor_effective`，也就是「这一维是被 floor 托住的」是可见的，不是暗改。

**A3 自适应会不会把一批全都脏的数据判成正常？**
答：会，这是自适应的固有盲区：整批分布偏移时 median 自己就跟着偏。兜底是两条熔断加数据集级 `stats_stale` 加人审。统计方法解决不了「全错」，我只能保证它不会静默通过。

**★A4 讲一个真实误报。**
答：一个真实数据集 50/50 episode 全报 action_jump，看下去是夹爪维只有 −1/+1 两个值，正常开合就是幅值 2 的跳变。修法是逐维数唯一值，`nunique ≤ 3` 判为离散维，delta 置 0 不参与连续跳变判定，被排除的维写进证据字段 `discrete_dims`。
数：`pipeline/validator/rules.py:107-115`（state 同构在 221-228）。
追：那离散维的真故障不就漏了？→ 对，那条规则不负责它，交给 `static_episode` 和质心时序；这是写下来的取舍，不是遗漏。

### B. 处置与清洗

**★B1 四档是怎么划的？**
答：按「证据强度 × 可修性」。error 且不可修 → drop；能确定性重写 → repair；规则判不了（跳变只超阈 1.02~1.35 倍这种）→ review 交人；其余 keep。
数：demo 13 处注入 → 7 drop / 2 repair / 3 review / 1 处降为 info 保留。
追：review 和 keep 差在哪？→ review 不进清洗，必须人签字；CSV 里带视频路径和时间窗，他不打开数据集就能定位那一段。

**★B2 到底能修什么？**
答：三类。边界 NaN 裁头尾帧；时间戳乱序按 `frame_index/fps` 整列重建；有删除时全局 index、meta 的 length、stats 全部按真实行数重算。中段 NaN 不修——补值就是工具在编训练数据，这件事我不做。
数：demo ep5 裁 3 帧、ep15 重建时间轴，清洗产物 29 ep / 2393 帧。
追：重建时间戳会不会跟视频错开？→ 裁剪和时间轴重建会同步重写 meta 里的视频时间窗和 length，产物末尾还有一道复检：用同一套规则引擎以流式重跑一遍清洗结果，`video_span_mismatch` / `frame_mismatch` 也在其中，drop 级不为 0 就把 `verification.ok` 置 false（`pipeline/cleaner/util.py:83`）。

**B3 删除为什么不自己实现？**
答：只有删除、没有修复项时我直接委托官方 `lerobot-edit-dataset`；一旦出现修复才走内置实现，因为官方 CLI 不做时间轴重建和 stats 重算。能少写就少写，官方行为跟下游 loader 一致，风险更低。

**★B4 熔断是什么？**
答：两道防止我批量删库的闸：某条规则命中超过 95% 的 episode，判定它大概是配错了——阈值配错通常就长这样，全部降级为 review；整体建议删除量超过 80%，也全部降级 review。被降级的会打 `source=systemic-guard` 写进报告，不静默。
数：`pipeline/policy.py:39` / `:42`。

### C. 安全与不变量

**★C1 怎么保证不动源数据？**
答：三道。清洗器入口断言输出目录与源数据集互不包含；`main.py` 在创建第一个文件之前就拒绝 `--output_dir` 落在数据集里；所有写入先落同一磁盘的暂存目录，校验通过才整体 rename 发布。
数：`pipeline/cleaner/util.py:20-27`、`main.py:164-171`、`tests/test_audit_hardening.py:537/551/567`。

**★C2 这个项目里你发现的最严重的 bug。**
答：是我自己的文档承诺和实现不一致，不是算法算错。README 写「源数据集严格只读，有单测保障」，但那道断言只做一个方向：输出目录在源数据集内部会拒，输出目录是源数据集的祖先不拒。而发布函数会先把最终路径改名成 `.prev-*`、再把旧目录整个删掉——路径配反时它删的是用户的源数据集。300 个测试全绿，因为没有一条用例把输出目录配在源的上方。我补了反向断言、入口断言和三条例外用例，之后给自己定了条规矩：文档里写「保证」，必须能指到一个用例。
数：`pipeline/cleaner/util.py:25-27` 就是那三行新断言。
（这题是全场最值钱的，务必练熟。）

**C3 为什么测试没暴露它？**
答：我的用例覆盖的是「业务会不会算错」，这条属于「运维会不会配错」，同一函数两种输入空间，我只测了前者。现在这类路径用负向用例钉住。

**★C4 发布中断会留下半个数据集吗？**
答：不会。Windows 上 `os.replace` 不能覆盖非空目录，所以先把旧目录 rename 成 `.prev-*`，新目录到位后再删旧目录；新目录到位失败就把旧目录退回原位。任何一步中断，最终路径上要么完整旧版、要么完整新版。
追：Ctrl+C 呢？→ 有用例专门验证暂存目录被清掉、旧产物没动（`tests/test_policy_cleaner.py:111`）。

**C5 退出码为什么搞这么多？**
答：给 CI 用的，不是给人看的。2 输入/配置问题；3/4/5 分别是质检/决策/报告阶段挂了；6 是 DEGRADED——链路跑完但清洗或点云失败被吞掉，这种绝不能当成功、也不能复用缓存；130 是 Ctrl+C。

### D. 点云

**D1 点云为什么要单独 8 条规则？**
答：它是定长向量列，不是图像。所以除了非有限值，还要看有效点数、包围盒退化、帧内重复比例、离群比例、工作空间越界、颜色通道越界、相邻帧质心/尺度突变。
数：`config/default.yaml` 的 `pc_*` 8 条。

**★D2 修复后为什么必须还是 N 个点？**
答：下游 DataLoader 要 `[N, D]` 的整齐批次。点数一旦可变，训练侧就得为清洗过的数据写特判分支，那这套东西没人会用。所以是过滤 → 去重 → 颜色裁剪 → 按场景尺度抖动重采样补回固定点数。
追：补出来的点是假的吗？→ 是重采样不是凭空造几何，notes 里显式写了怎么补的，不装成原始观测。
数：`pipeline/pointcloud/cleaner.py:179-180`。

**D3 不可修的帧怎么办？**
答：不删行，用上一帧有效点云 hold-last-good 占位，保住 parquet 行数与视频/state 对齐。删一行就得重编码视频，又慢又容易错位。

**D4 离群半径怎么定？**
答：每帧先算 1-NN 距离中位数，半径 = 中位数 × k。固定比例在稀疏点云会全帧误报——我第一版就是这么错的。

### E. 性能与规模

**★E1 14 GB 的数据集怎么跑得动？**
答：三条。只读需要的列，逐帧表不整张进内存（流式按 parquet 分片扫）；统计用 Welford 在线累加加蓄水池采样，不物化大数组；视频不整段解码，探针三级——`stream.nb_frames` → `duration×fps` → 必要时才解码。
数：schema 审计读 2 列、14 GB 约 1.3 s；demo 全流程约 14 s；`--workers 8` 190.1 s → 64.7 s。
追：流式和全量结论一样吗？→ **不一样，这是我这轮外部交叉验证里最严重的一条。** 阈值和 stats 来自采样只是已知的差；真正的问题是「复用规则 ≠ 复用输入」。libero（1693 ep）全量模式 keep 1692 / review 0，同一份数据 `--streaming` 给到 review 1692、health 直接判 `severe`、valid_ratio 0.0、建议「先修采集流程」。根因：`task_of()` 拿任务文本只有两条路——`meta/episodes` 的 `tasks` 列，或逐帧 `task_index`；libero 的 episodes 元数据没有 task 列，而流式和 precheck 都不把整张逐帧表读进内存，两条路同时断掉 → 1693 集全判 `missing_task`。修法是流式分片时顺手聚合 `episode_index → task_index`（每集一个整数，不需要留整表）。最扎心的是第三条路径：清洗跑完后流水线会自动复检产物，那份报告里结构层 `verification.ok=true`、编号连续、帧数逐位对上，规则层却写着 `review 1692` 和「建议跑完整流水线修复」——它对自己刚洗干净的数据集给出「还得再修」，我自己第一遍看到时以为是清洗出了问题。修好之前，`--streaming`、precheck 和清洗产物复检的结论都不能当全量用——这条落在 `docs/EVAL.md` §2.5 的 M1。

**★E2 并发怎么保证结果一致？**
答：计算与落盘分离——worker 是纯函数，只回传可 pickle 的结果，主进程是唯一写者；future 完成顺序随机，所以归并后按 key 排序重建，测试直接比 `json.dumps(sort_keys=True)` 的字节。
数：`tests/test_parallel.py:29-59`。

**E3 增量模式怎么做对的？**
答：manifest 存每个 episode 的签名，里面含解析后的阈值，阈值随数据变了缓存就失效、回退全量重检；复用的结论是完整的 `EpisodeResult.to_dict()`，带 `severity_overrides`——少了这一项，同一份数据二跑会从 info 退回 warning，keep 和 review 之间会漂。
追：缓存的清洗产物可信吗？→ 校验没过（`verification.ok=false`）的缓存会在 `main.py:606` 被拒绝复用。

**F1 为什么不直接用 DVC？**

### G. 结果与局限

**★G1 效果怎么量？**

**G3 为什么不用 ML 做质检？**

**G4 有没有现成工具比你做得好？**
答：有。`lerobot-doctor` / DataDoctor 有 URDF 物理限位校验和全帧解码审计，我都没有——限位要外部真值，19 个数据集大部分拿不到；全帧解码在几十 GB 上不划算。我自研只有三条理由：我要处置不要结论；源数据不能被改（它的 `fix` 原地重写 parquet，而备份只 `copytree` 了 `meta/`，这点我读过它源码）；子集模式要诚实——覆盖不足我拒绝导出，退出码 3。

**G5 重做一次会改什么？**
